# AB Testing: From SQL to Decision

## TL;DR

Полный пайплайн анализа A/B-теста: от сырых логов событий (SQL) до
статистического анализа (Excel + Python) и итоговой бизнес-рекомендации.
На примере теста новой версии онбординга — обе ключевые метрики
(выручка, конверсия) показали статистически значимый рост.

## Задача

Тестируем гипотетическую новую версию онбординга (группа B) против
текущей версии (группа A). Нужно понять, увеличивает ли новая версия
выручку с пользователя, не ухудшая при этом конверсию в покупку.

## Гипотезы

**Revenue (Welch t-test):**
H0: μ_A = μ_B (средняя выручка одинакова)
H1: μ_A ≠ μ_B

**Конверсия (z-тест):**
H0: p_A = p_B
H1: p_A ≠ p_B

## Пайплайн

1. **Генерация данных** — синтетический датасет, имитирующий сырые
события покупок (Excel + Python для разворачивания множественных
покупок на пользователя)
2. **SQL** — агрегация сырых событий в метрики на уровне пользователя
(LEFT JOIN + GROUP BY)
3. **Проверка SRM** (Sample Ratio Mismatch) — убеждаемся, что
пользователи корректно разделились между группами
4. **Power analysis** — обоснование необходимого размера выборки
5. **Статистический анализ** — Welch t-test для выручки, z-тест для
конверсии (Excel + сверка в Python)
6. **Итоговая рекомендация** — вывод в бизнес-формулировке

## Результат
Тест показал статистически значимый рост обеих метрик в группе B:
- Средняя выручка на пользователя: 324₽ → 436₽ (+35%, p-value ≈ 0.005)
- Конверсия: 15.0% → 20.0% (p-value ≈ 0.003)

В обоих случаях p-value меньше выбранного уровня значимости α=0.05, 
поэтому обе нулевые гипотезы (H0) отвергаются — различие между 
группами статистически значимо, а не объясняется случайностью.

## Ключевые методологические решения

- **SRM-проверка перед анализом** — стандартная практика в индустрии,
подтверждает, что группы разделились корректно (~1000/1000)
- **Welch t-test, а не обычный t-тест** — дисперсии в группах не
гарантированно равны, тест Уэлча безопаснее по умолчанию
- **Power analysis** — заранее обосновано, что 1000 наблюдений на
группу достаточно для обнаружения ожидаемого эффекта (требовалось
~800 при заданных параметрах)
- **Guardrail-метрика (конверсия)** — проверена отдельно от основной
метрики (выручки), чтобы убедиться, что улучшение не сопровождается
скрытым ухудшением
